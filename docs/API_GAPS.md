# Koomyo API gaps and decisions

This file lists what the Koomyo public API and its docs (docs.koomyo.com, `openapi.json` v1.0.0, read 2026-10-26) do not give yet, and the choices the app makes where the docs leave room. Each entry says what is missing, why it matters, what the app does about it, and what would fix it.

Status keys: **Open** (waiting on Koomyo), **Decision** (the app chose; the owner should confirm), **Blocked** (that part is not built), **Resolved**.

---

## 1. Where the feed starts (Resolved)

`GET /events` now answers `oldest_seq`, `latest_seq` and `gap` (docs: events/feed#how-long-events-are-kept; schema `EventList`). `gap` is true when events between our `after` and `oldest_seq` were deleted, never for `after=0`, and the same whatever `types` or `branch_id` filter is used (so it can be true when what was deleted was of no interest: the safe side).

- The 29-day guess (`FEED_SAFE_DAYS`) is removed. Only `gap` stops the feed.
- On a gap the feed is not read on. The connection is marked Needs Re-sync, the alert goes out, and a Backfill for the days since the last complete read is made and started (`sync/resync.py`); when it completes without failures the feed continues from `latest_seq`. A range longer than one backfill (366 days) is cut at 365 days: older days need their own backfills. Stock before the Opening Stock Date is left out, as everywhere.
- A Koomyo that does not send the three fields is read as having no gap; nothing is guessed from time.
- `gap` true without a `latest_seq` stops with a message and no automatic re-sync (there is no head to continue from).
- **Not verified live.** The fake Koomyo plays the signal; the live API was not made to delete events.

## 2. Scope list in CLAUDE.md (Resolved)

CLAUDE.md now lists `suppliers.write`, `ingredients.write` and `refs.write`, matching `reference/scopes`. Each sync declares the scopes it needs, and Test Connection shows the missing ones for the syncs that are switched on.

## 3. Events feed pages by number (Resolved)

CLAUDE.md now says the feed pages by event number. The app stores `last_seq` per connection, taken only from `next_after`. List endpoints keep their opaque `next_cursor`.

## 4. A refund carries an amount, not lines (Decision)

**What.** The `Refund` schema has `amount`, `payment_method` and `reason`, but no lines. Koomyo's own ERPNext guide says a partial refund "needs a decision from your accountant".

**What the app does.**
- A refund of the whole invoice becomes a Credit Note that mirrors it exactly, using ERPNext's own `make_sales_return`.
- A partial refund follows the connection's **Partial Refunds** setting:
  - **Leave for Manual Booking** (default, the safe choice): the event fails with a message naming the invoice and amount, so a person books it by hand, or changes the setting and presses Retry.
  - **Proportional Credit Note**: every tax and charge row is reversed in the share `refund / invoice total`, rounded to the cent. The revenue line takes the rounding, so the Credit Note total equals the refund exactly. Tests check that two partial refunds add back up to the original tax.

**Update (refund `lines`, built).** `Refund.lines` [{line_id, name, quantity, amount}] is now in the API, filled only for the order's only refund that pays back everything collected (`amount` is the line's net price); every other refund, including each amount-only partial refund, has `lines: []` and nothing is guessed. That refund is the full mirror credit note, which already is every line. The lines are checked against the invoice: each `line_id` must be a row (rows now carry the Koomyo line id in a hidden `koomyo_line_id` field), at its net amount, and the count must match, else the refund fails (Fatal) with the line named; an invoice booked before the field existed is taken as it is. A partial refund stays an amount: no by-line credit note exists for it because Koomyo never says which lines. Not run against live Koomyo (the docs' example lines do not match its own order example, so tests use consistent ones).

## 5. Menu items, stock on sales invoices, and card fees (Decision)

- **Menu items.** Each Koomyo menu item (or combo) becomes one non-stock ERPNext Item, made the first time it is sold, in the connection's Menu Item Group. It is matched by `(koomyo_connection, koomyo_id)`, so two restaurants never share an Item. Modifiers and combo upgrades are an extra line, so each Koomyo `line_total` is kept exactly.
- **No stock on Sales Invoices.** Koomyo already deducts recipe ingredients, so invoices never move stock (`update_stock = 0`); stock comes from the stock sync. There is no switch for this: a switch to move menu-item stock would double-count.
- **Card and wallet fees.** Koomyo does not report provider fees. Each Payment Map row can hold a fee percent and a fee account, and the fee is booked as a deduction on the Payment Entry. Leave it at 0 when fees are booked from bank statements.
- **Tax-inclusive prices.** ERPNext's "included in print rate" recomputes tax and can differ from Koomyo by a cent. The app instead adds two exact rows: the tax moved out of income, and the tax to the tax account.

## 6. Shift close: refunds and rider cash in the variance (Resolved)

Koomyo confirmed (OpenAPI `Shift.refunds`, docs events/cash): `expected_cash` is opening cash + the shift's cash payments + `rider_cash_handed_in` at that till, and it does NOT subtract refunds. `refunds` is `{count, amount, cash_amount}`: `amount` is every refund made while the shift was open, whatever way the money went back, and `cash_amount` is the part paid back in cash from the drawer.

- The Journal Entry books `counted_cash - (expected_cash - refunds.cash_amount)` between the drawer account and the Cash Over/Short account (`sync/shifts.py`). `refunds.amount` is no longer used (a card refund is not cash out of the drawer). A shift stored before Koomyo sent `cash_amount` falls back to `amount`. Koomyo's own figures must still add up (opening + cash taken + rider cash = expected; counted - expected = variance) or nothing is booked.
- **Rider cash.** A rider's collect-on-delivery payment is an order payment that belongs to no shift, so it is not in any shift's `payments_by_method`; a hand-in at a counter is a settlement against the receiving cashier's open shift (that shift's `rider_cash_handed_in`, in `expected_cash`); a hand-in settled from the admin goes to no till. The order's Payment Entry still lands in the mapped cash account when the order is paid, so the rider cash is already in ERPNext's cash account; the hand-in changes nothing there and only enters Koomyo's expectation. A hand-in settled from the admin panel therefore also leaves the drawer figure alone.
- **Caveat from the docs.** A refund's shift is the most recently opened open shift at the time of the refund, so a refund can be counted in a shift other than the one whose drawer it came from when several tills are open. The over/short of such a shift is then off by that refund, and the opposite way on the other; the remark shows the figures.
- Tests replay the docs' day (cash account ends at counted minus float), a card refund that must not touch the drawer, a mixed cash and card refund, rider cash at the till, and a shift without `cash_amount`. Not run against a live Koomyo.

## 7. Stock: menu-item waste, short transfers, central warehouses, valuation (Decision / Open)

- **Waste lines (Built).** `GET /waste` and `waste.recorded` carry `lines` [{ingredient_id, ingredient_name, quantity (positive), unit, unit_cost, value}] read from the stock the waste took out: a menu-item waste has one line per recipe ingredient, an ingredient waste has one. The Material Issue is booked from `lines` (one row per line, at ERPNext's own valuation; Koomyo's `unit_cost` and `value` are not used, as for other issues). Empty `lines` with an ingredient present (free text) books the waste's own ingredient and quantity as before. Empty `lines` on a menu-item waste still fails with a message: it is waste from before movements were kept, or a cancelled order logged as waste whose ingredients are in the order's own `order_deduction` movements, so booking them again would count them twice. A person's own `unit_cost` can make the line costs differ slightly from the waste's `value`. The backfill of waste uses the same handler. Not run against live Koomyo.
- **Transfers in steps (Decision, replaces the old "arrive short" note).** Koomyo now sends `transfer.sent`, `transfer.received` (one per delivery; the entity is the receipt), `transfer.short_closed` (returned / lost, with reason and value) and `transfer.cancelled`, and keeps `stock_transfer.completed`. Every event carries the transfer as it stands, so one routine (`sync/transfers.py: reconcile`) posts what is not booked yet, whichever event brings it. With a Transit Warehouse set: send = Material Transfer with `add_to_transit` into transit; each delivery = ERPNext's `make_stock_in_entry` from transit (keyed by receipt id); returned = the same back to the source; lost = Material Issue from transit to the Transfer Loss Account (ERPNext values it at the stock's own cost; Koomyo's `value` and reason go in the remarks); cancelled = cancel the send. Without it the old one-step behaviour of `stock_transfer.completed` stays (what arrived moves, the shortfall is a loss), and the step events are skipped with a message. A transfer sent before the Opening Stock Date is left out (it is in the opening stock). Entries made by the old one-step flow are never doubled by the steps. Not verified: any live transfer (the restaurant has none); the fake Koomyo plays the docs examples.
  - `transfer.cancelled` fires only for a draft or a sent transfer where nothing has arrived; once a delivery exists the transfer is resolved (returned or lost) instead. So a cancel never meets a booked delivery. The app still refuses to force it (the event fails with a message) in case a delivery was booked by hand in ERPNext against the send entry.
  - **v16.** `add_to_transit` / `outgoing_stock_entry` are the v15 mechanics; v16 was not run.
- **Central warehouses (Built).** `GET /warehouses` (scope `stock.read`; id, name, address, active, is_main) is read by Set Up From Koomyo: every active warehouse gets a Branch Map row of Location Type Warehouse (an ERPNext Warehouse of the same name, used if it exists, else created), and Koomyo's main warehouse is proposed as the connection's Main Warehouse. A purchase order that names a `warehouse_id` is booked into the Warehouse mapped for it (an unmapped one fails with its id). If the endpoint answers 403 or 404 (no Inventory app), the older way is used: warehouses seen as an end of a stock transfer. Not run against live Koomyo: the fake plays the endpoint.
- **Daily usage has no id.** Koomyo says a day is sent once per branch, so the Stock Entry is keyed `usage:<branch>:<business_date>`. A day with more put back than used (net negative) gets a separate Material Receipt keyed `...:returned`.
- **Valuation.** Stock leaves at ERPNext's own valuation, as the docs suggest ("If your ERP values stock itself, use only quantity_used"). Stock comes in (adjustments, counts) at Koomyo's `unit_cost`. ERPNext's cost of goods can therefore differ from Koomyo's `cost` when the two valuations differ.
- **Not enough stock in ERPNext.** Koomyo allows negative stock and ERPNext by default does not. Such an event fails with ERPNext's message. Set the opening stock (and the Opening Stock Date), or allow negative stock in Stock Settings, then press Retry.
- **Quantities.** Koomyo sends up to 4 decimals. They are stored as ERPNext floats and may be rounded to the site's float precision (3 by default). Money is not affected.

## 8. Purchasing and customers (Decision / Open)

- **Several deliveries per order through the public receive (Built).** `POST /purchase-orders/{id}/receive` is one delivery per call, with its own `receipts[]` entry; `quantity_received` is the line's TOTAL so far and only the difference is added to stock; the order is `partial` until every line is complete or `close_short` is true. Each ERPNext Purchase Receipt is sent as one call: per line, Koomyo's current total (read just before) plus this receipt's stock quantity; `delivery_note` from the receipt's Supplier Delivery Note (80 characters). The new `receipts[]` entry is stored on the Purchase Receipt (`koomyo_id`), so the `purchase.received` event that follows books nothing. `409 nothing_to_receive` is Skipped (Koomyo already holds the quantities), `409 already_received` fails with a message saying the order is fully received or closed short, `400` (a total below what is received) fails as an API error. A Purchase Order a person Closes in ERPNext after part arrived is sent as `close_short` with the current totals (an empty body would receive everything); an order Koomyo shows as not partial is Skipped. ERPNext's Close button fires no document event, so closed orders are looked for every 5 minutes (`queue_closed_orders`). `received_by` is left out so Koomyo uses the key's name. Not verified live: the fake Koomyo plays the documented rules.
- **Which orders are sent.** A Purchase Order is written to Koomyo only when its Warehouse is on a connection's Branch Map. Branch rows send `branch_id`; central-warehouse rows leave it out, so the order goes to Koomyo's main warehouse. One Warehouse per order, and one line per ingredient. Only Items linked to a Koomyo ingredient can be ordered.
- **Quantities and costs** go out in the ingredient's stock unit: `stock_qty`, and `base_net_rate / conversion_factor` in company currency, up to 4 decimals.
- **Suppliers are not shared between connections.** A Supplier carries one Koomyo link. Using it for a second connection's order fails with a message to make a separate Supplier.
- **Ingredient cost.** The push is triggered by a person changing an ingredient Item's Valuation Rate, through `PATCH /ingredients/{id}`. ERPNext's moving-average valuation after receipts is not pushed automatically.
- **Koomyo-made purchase orders.** A `purchase.received` for an order created in Koomyo (no ERPNext Purchase Order) is skipped with a message. ERPNext is the source for purchasing. Supplier and ingredient events from Koomyo (`supplier.*`, `ingredient.*`) are not synced into ERPNext.
- **Customers are one way, Koomyo to ERPNext.** Only name, phone and email are copied, and the ERPNext id is stored on the Koomyo customer with `PUT /refs/customer/{id}`. ERPNext customers are not created in Koomyo, so `customers.write` is not used. Customer events arrive only when the webhook's customer data switch is on.
- **External references written.** Supplier and purchase order references go in the create call. Customer and ingredient references use `PUT /refs`. Orders, refunds and shifts are not given references, to save the rate limit; the ERPNext documents carry the Koomyo id instead.

## 9. Backfill (Decision / Blocked)

- **Manual stock adjustments are not backfilled (Blocked).** `GET /stock-movements` lists every movement, and its `reason` is "a system code such as order_deduction, order_cancel_restore or po_received, or the text a person typed". The docs name only `order_deduction`, `order_cancel_restore`, `po_received`, `transfer_out` and `transfer_in`, not the codes for waste or count movements. So a manual adjustment cannot be told apart safely from movements booked another way, and counting it twice would corrupt stock. Live `stock.adjusted` events are booked as usual. Backdated manual adjustments must be entered by hand. **Wish:** a documented list of reason codes, or a `kind=manual` filter on `GET /stock-movements`.
- **Daily usage comes from `GET /stock-usage` (Built).** The backfill reads `GET /stock-usage?business_date=<day>[&branch_id]` (scope `stock.read`, Inventory app): the exact objects of `stock.usage_daily`, one per branch that used ingredients, ordered by branch id, booked through the same handler under the live key `usage:<branch>:<day>`, so a day that came live is "already there" and a day brought by backfill is not doubled when its event arrives. Summing movements is gone. A day Koomyo has not settled yet (the event is sent an hour after the restaurant's midnight) answers `409 day_not_settled`: that is not an empty day. The backfill counts it as skipped, says so in the day's message, and the day can be run again alone later (Run Day Again). Per-order days are still skipped. Not run against live Koomyo: the fake plays the endpoint and the 409.
- **Which orders.** Orders with `payment.status = paid` on each business day (`GET /orders?business_date=&payment_status=paid`). A paid order cancelled later is still a sale, and its refund comes in through the refund list.
- **Lists without a day filter.** Refunds, shifts, waste, counts and transfers are read with a wider UTC window (`created_after`, `opened_after`, `sent_after`) and picked by `business_date`. Customers (`updated_since` = From Date) and received purchase orders (no date filter, picked by `business_date`) are one part each.
- **Closed periods.** The run is refused, naming the reason, when the range touches any of: an Accounting Period closed for a document type it would post; a submitted Period Closing Voucher ending on or after From Date; the Accounts Settings freeze date; or, for stock and purchases, the Stock Settings freeze date.
- **Pacing.** Each call checks `X-RateLimit-Remaining`. When fewer than a tenth of the key's allowance is left, the run waits for it to refill. A 429 is waited out (`Retry-After` plus one second) and the same page is asked for again. The position (Koomyo's opaque `next_cursor` per list) is saved after every page, so Stop, a crash or a restart carries on from there.

## 10. Complaints (Built)

Koomyo's complaints are in the API now: `GET /complaints`, `GET /complaints/{id}`, `GET /complaint-categories`, `complaint.created` and `complaint.updated`, scope `complaints.read` (docs: events/complaints, guides/orders-and-complaints). Only restaurants with the Complaints app have them.

- **Built:** the switch **Sync Complaints** (Syncs tab) turns each complaint into one Issue keyed (connection, complaint id), brought up to the newest copy by `updated_at` on every event (`sync/complaints.py`). Status: new, acknowledged and in_progress are Open, waiting_customer is On Hold, resolved is Resolved, closed is Closed. Priority: low is Low, normal is Medium, high and urgent are High. The resolution summary and its cost go to the Issue's resolution details. The order number, category, channel, SLA dates, overdue flag, photo count and reopen count are plain lines in the description.
- **Privacy.** The customer's name and phone are never copied (the event may carry them with `customers.read`). An Issue is linked to a Customer only when Koomyo's customer id is a Customer already synced for the connection. The summary and description are text typed by staff or the customer, so they can mention a name; they are kept as written and escaped.
- **Not built:** the timeline, photos and resolution records (`GET /complaints/{id}` only), writing back (`POST /complaints`, notes, status: scope `complaints.write`), a backfill kind for complaints (the 30-day events feed and its re-sync cover them), and a mapping of Koomyo categories to Issue Types.
- **Not verified live:** the restaurant has no complaints; the docs examples run through the fake Koomyo.

## 12. Per-order stock deduction (Decision)

**What the app does.** With Stock Deduction set to Per Order, each `order.paid` queues a stock step. The step reads `GET /stock-movements?reason=order_deduction&reference_id=<order id>` (the filter Koomyo added; no time window any more) and keeps the rows whose `reference_id` is the order. They become one Material Issue (key `order:<id>`). `order.cancelled` does the same with `order_cancel_restore` and makes a Material Receipt (key `order-restore:<id>`). Daily usage is skipped on per-order days. A change of setting applies from the next day, so a day is never booked both ways.

- Docs (reference/stock-movement-reasons): for an order movement `reference_id` is the order id; `packaging` movements also carry it (packaging items) and are not booked here, as before. Not run against live Koomyo: the fake plays the filter.
- **Manual adjustments in a backfill.** A backfill of stock now also brings in `GET /stock-movements?kind=manual` rows (a person's hand adjustments, free text reasons) as `stock.adjusted` with the live key (the movement id), so a live event and a backfill never double. `stock_count` and `non_sale_usage` movements are left out because counts and waste have their own events and backfill kinds, and `opening_stock` is left out because it is already in the opening stock. If Koomyo's live `stock.adjusted` also fires for those, the keys still match nothing here, so nothing is booked twice either way.

## 13. Sizes, modifiers and categories (Decision / Open)

- **Sizes are Item Variants.** A menu item with sizes is a template Item, keyed by the Koomyo menu item id. Each size is a variant on the "Koomyo Size" attribute, keyed by the Koomyo `size_id`, with its own price on the selling price list (ERPNext does not price templates). An order line with a `size_id` books on that variant. A size dropped in Koomyo is disabled, never deleted. An Item that already has invoices or stock as a plain Item cannot become a template in ERPNext, so it keeps taking all its sizes.
- **Modifiers and combo choices are not separate Items.** `list_price`, `unit_price` and `line_total` on an order line already include the chosen options (docs guide: 1099 = 1000 + 99), so the line is one invoice row and the old "extras" row is gone (see item 15). Every modifier, free ones included, is written in the line's description. Their ingredients reach stock through Koomyo's own deductions.
- **Options read for costing only (item 16).** `GET /option-groups`, `GET /option-groups/{id}` and the menu item `include=options` exist now (scope `catalog.read`). The app reads them for costing and bills of materials, never for stock: `sync/recipes.py` has the docs' `stockForLine` arithmetic in exact Decimals (item recipe for the size, each chosen option's rows for the size, swaps giving the replaced ingredient back as a negative use, times the quantity), the match of an order line's `modifiers[].modifier_id` to an option (an unmatched modifier is reported, never guessed) and cost from ingredient costs. Load Menu and Ingredients reads the groups and says how many, how many take nothing from stock, and which recipes count an ingredient twice.
- **Categories are Item Groups.** One leaf group per Koomyo category, named "<category> (<connection>)", under "<connection> Menu". Items without a category go to the connection's Menu Item Group. A category renamed in Koomyo gets a new group on the next load, its items move there, and the old group is left for you to remove.

## 14. Purchase orders made in Koomyo (Decision / Open)

Source: docs.koomyo.com/events/purchasing and /guides/stock-purchasing, schemas `PurchaseOrder`, `Event_Purchase*`.

- `purchase.created|updated|cancelled|received` and the `GET /purchase-orders?updated_since=` safety net (queued as `koomyo.purchase_sync` Event Log rows every 5 minutes, cursor on the connection) all run through `apply_order`. A draft creates nothing (the sync does not even queue one). Copies older than the booked `updated_at` change nothing.
- With Book Orders Made in Koomyo on, `ordered` or later makes a submitted Purchase Order and Supplier. Orders made in ERPNext are never rebuilt (only receipted and cancelled), and Koomyo-made orders and suppliers are never sent back. A Koomyo supplier whose name exists in ERPNext is created as "<name> (<connection>)", never merged. Orders without a branch go to the Main Warehouse.
- **An edit cancels and remakes the Purchase Order** (a submitted order cannot be edited), only when the goods, supplier, charges or tax changed (a fingerprint on the order; a send by email or an expected-date change does not). The cancelled order gives up its Koomyo id. After a delivery, only notes are copied: Koomyo says the same, only notes and the date can change then.
- **A cancel** cancels the counterpart; if goods were already received in ERPNext it fails with a message for a person and cancels nothing (press Retry after dealing with the receipts).
- **Each delivery is its own Purchase Receipt**, keyed by the receipt id, dated by the restaurant's day of `received_at`, carrying the supplier's delivery note. A Purchase Receipt made in ERPNext and sent to Koomyo is linked to the delivery Koomyo creates for it (its `receipts[]` entry) and never doubled. An order received before Koomyo kept deliveries (no `receipts`) is one receipt keyed by the order id.
- Money: line net = `line_total - tax_amount`; the order's tax lines, withholding and charges are Actual rows (see the README section Purchase taxes and charges). ERPNext's total must match `total_ordered` to within a cent per row, else nothing is booked.
- **Unverified.** Only the fake Koomyo and the docs examples were used: no live order with tax, withholding or charges (the live restaurant has none). Costs with many decimals can differ from Koomyo's by a few paisa after ERPNext rounds each rate.
- Outbound is unchanged: ERPNext sends the order's one public receive (`already_received` is reported clearly), see item 8.

## 15. Discounts on sales (Decision / Open)

Source: docs.koomyo.com/guides/discounts and the OpenAPI schemas `OrderLine`, `Order`.

- Each line is posted at `price_list_rate = list_price`, discount per unit `list_price - rate`, `rate = net_price / quantity`. "Enable Discount Accounting for Selling" is switched on at install and by a patch; with it off a discounted order fails with a message saying so, instead of posting a wrong book.
- Each source (`promotion`, `voucher`, `manual`, `points_reward`, `slice_reward`, `gift_item`) has an account in the connection's **Discount Map**; an unmapped source is `Failed: NeedsMapping` naming the row. ERPNext takes one discount account per line (and one for the order), so a line or order that mixes sources is posted on its largest part and a Journal Entry (`koomyo_id` = `discount:<order id>`) moves the other parts to their own accounts. A full refund reverses that entry (`discount-refund:<refund id>`). A refund's `discount_given_back` (its share of the order's discount by source, now in the API) is used for every refund that carries it: a partial Proportional Credit Note is built at the price before the discount with the discount shown, so income and the discount account are reversed by the share Koomyo names, and a Journal Entry (`discount-refund:<refund id>`) moves each source's part to its own account (read from what the credit note actually posted, so ERPNext's own rounding is respected; a difference of a cent stays with the largest part so the entry balances). A full refund does the same and so reverses the order's reclassification exactly. Across several partial refunds a source can differ from its total by a cent or two (the docs say so). A refund without the field (an older Koomyo, or an order with no discount) keeps the old behaviour: net revenue only, and the order's reclassification reversed only by a full refund. A split needs Enable Discount Accounting for Selling (else NeedsMapping), and a source with no Discount Map row names the row.
- Tax is Koomyo's `tax` as sent, never recalculated. Quantity above 1 with a net that does not divide to the cent becomes two rows (the last unit takes the odd cent), so the invoice still equals `net_price` exactly.
- A gift item stored before Koomyo kept prices has null `list_price`: it is posted at its net price with no discount and a note on the row, nothing is guessed.
- If a line's `discounts` parts do not add up to `list_total - net_price`, the whole discount goes to the largest part's account and a note is added to the invoice remarks.
- The identity `items_list_total - discount_total = items_subtotal - discount - voucher_discount` is checked when the order carries both totals; a break is Fatal and nothing is booked.
- Channel `api` orders are ordinary sales. Stock is not moved by the invoice (Koomyo deducts ingredients itself).
- **Not verified against a live order with a discount** (the only live connection has none). Verified on the local test site with Koomyo's documented numbers (GL entries asserted).

## 16. Options and bills of materials (Decision / Open)

- Koomyo deducts ingredient stock itself, so options change nothing in ERPNext stock: the invoice does not move stock and the per-order deduction copies Koomyo's own movements (item 12).
- **No event when an option changes** (docs: "Staying in step"). The app does not keep a copy; Load Menu and Ingredients reads the groups again on request. Cost and BOM work should read `GET /option-groups` just before it runs.
- **Bills of materials are not built.** An ERPNext BOM is a manufacturing document, and CLAUDE.md puts manufacturing out of scope for v1. The calculator and the reader are ready (and tested against the docs' Thin Crust example); a BOM per menu item and size, with each option as an optional row, is a small step if the owner puts it in scope. Items made from menu sizes are variants, so a BOM would hang on the size variant.
- A row with no size stacks on a row for one size (the docs say so and warn that Koomyo's admin does too); the arithmetic follows Koomyo. A size with a price and no recipe row takes nothing.
- **Not verified live.** The live restaurant's options were not read; the fake Koomyo serves the docs' example.

## 17. Suppliers (Decision / Open)

Source: docs.koomyo.com/events/master-data, schema `Supplier`.

- `supplier.created|updated` (switch: Book Orders Made in Koomyo) make or update a Supplier, one Billing Address, one Contact and a Payment Terms Template (`sync/suppliers.py`). A copy older than the stored `updated_at` changes nothing. Koomyo's `POST /suppliers` with our external reference fires `supplier.updated`; that echo is skipped because the Supplier is ERPNext-made.
- ERPNext has no field for the credit limit, lead time, minimum order, delivery days, tags, preferred flag, rating, code, second tax number or tax status of a supplier, so they are written as plain text in the Supplier's "More Information" (escaped). `tax_status` is not mapped to a Tax Category (the app does not guess which of the site's categories means "registered"). Payment terms `advance` has no ERPNext meaning beyond "due on the invoice date"; the template says so in its description.
- The address needs a first line, a city and a country ERPNext knows by name: Address requires all three. Otherwise no address is made and the Supplier gets a comment saying what was missing. The country is matched by ERPNext name only (capitals ignored); nothing is guessed from a code.
- **Not pushed back.** ERPNext still sends only name, active flag, phone and email (`POST /suppliers`); the fuller card is read-only here. **Wish:** none needed unless the owner wants edits to flow back; then `PATCH /suppliers/{id}` has the fields.
- **Backfill (built).** A Koomyo Backfill with **Purchases** ticked reads `GET /suppliers` (scope `purchasing.read`, cursor paging) and brings every supplier made up to the end of the range through the same handler as `supplier.updated` (needs Book Orders Made in Koomyo on). A supplier has no business date, so the range only cuts off suppliers created after it. A supplier already in ERPNext with this card (or a newer one) counts as already there; one made in ERPNext is left alone; a changed card is brought up to date. Suppliers are read before the purchase orders of the same run. Backfill events for suppliers, customers and purchase orders now carry the record's `updated_at` in their id, so a run after a change is not mistaken for a repeat.
- **Processing user.** Events are booked as Administrator, whoever queued the job: a Koomyo Manager who pressed Retry or Catch Up Now used to get a PermissionError when Koomyo cancelled a purchase order or transfer, or when an order named a supplier ERPNext did not have yet.
- **Not verified live:** only the docs examples through the fake Koomyo.

## 18. Names of customers and suppliers (Decision)

- A Customer is named from Koomyo's name; with no name, from the phone number; with neither, "Koomyo customer <first 8 characters of the id>". Koomyo's full id is never used as a name (it is kept in the Koomyo Id field). A later event without a name never replaces a name already there, and a real name that arrives later renames the Customer and its primary Contact (first and last name split as ERPNext does). A changed phone or email becomes the Contact's primary one; the old one stays as a row. The same label rule applies to a supplier card without a name ("Koomyo supplier <8>"); Koomyo's schema makes the name required, so this is a guard.
- ERPNext's own document names follow Selling Settings (Customer Name or Naming Series); that setting is the site's, not the app's.
- Contacts made for Customers carry no Koomyo fields. Contacts and Addresses made for Suppliers carry the supplier's Koomyo id in `koomyo_id` (so a later update finds them), never in a name.

## 19. Purchase requests, consolidated orders and receiving per place (Decision / Open)

Source: docs.koomyo.com/guides/purchase-requests and /events/purchase-requests, OpenAPI `PurchaseRequest*`, `PurchaseOrderAllocation*`, `POST /purchase-orders` (`deliver_to`, `allocations`), `POST /purchase-orders/{id}/receive` (`destination_type`, `destination_id`, `reason_code`, `reason_note`).

- **Material Request mapping.** One request is one Material Request (type Purchase, submitted), made when a line is approved and containing the lines with status approved, ordered, partly_received or received at `approved_quantity`. A line waiting for purchasing, rejected or cancelled is not in it. A request waiting for the branch manager has nothing approved, so nothing is made. Not decided by the docs and chosen here: a Material Request cannot be edited once submitted, so a change of the approved set or quantity cancels and remakes it, which is refused (event Failed, nothing forced) once a Purchase Order, Stock Entry or quotation was made from it. Progress (ordered, received) never rebuilds anything. The app does not push ordered or received quantities onto the Material Request: ERPNext computes its own.
- **Branch Warehouse.** The Material Request row's Warehouse is the branch's Warehouse on the Branch Map; a branch with no row is `NeedsMapping`.
- **Writing the order.** A Purchase Order whose rows come from Koomyo-linked Material Requests is sent with `allocations` (the Koomyo request line id is kept on each Material Request row) and no `branch_id` (the shares carry the branches). Rows of one Item are summed into one line (Koomyo wants one line per ingredient and one share per request line), at one rate (different rates are refused before anything is sent). A Purchase Order with some rows from requests and some from none is refused (every row must fill a request line). `deliver_to` is sent only when the connection says so; "Koomyo Decides" leaves it out so Koomyo uses its main warehouse when it has one, else the branches. Koomyo's refusals (400 `invalid_parameter`, 409 `request_line_not_orderable`, 409 `request_quantity_exceeded`, 403 `feature_not_available`) fail the event with plain advice and create nothing. A retry after a refusal uses a fresh Idempotency-Key. Koomyo confirmed it stores and replays every refused (4xx) answer for the same key, with `Idempotent-Replayed: true`; 5xx answers are not stored, so the same key can be retried after a server error. `external_ref` still makes the order unique.
- **Both orderers.** If Koomyo's own staff also order, whoever orders a line first wins; the second is refused. The setting that stops this (ERP mode) is not readable by the API, so the app cannot check it (now readable: `GET /account` has `purchase_requests: {enabled, handled_by}`; see below): the connection form and the README tell the user to set it and not to press Send on an order ERPNext made (Send emails the supplier).
- **Receiving per place.** An order whose lines carry allocations is received by destination: one call per Warehouse of the Purchase Receipt, found on the Branch Map (a branch row is `branch`, a row of Location Type Warehouse is `warehouse`); `quantity_received` is the line's total at that place (the shares' `received_quantity` there, plus this receipt). A receipt spanning two places makes two deliveries: the first Koomyo delivery id is the receipt's Koomyo id and the others are listed in a hidden field, so none is booked twice when its `purchase.received` arrives. `reason_code` and `note` on a line are not sent (ERPNext has no matching reason on a receipt; it is optional). A Purchase Order closed in ERPNext is sent as `close_short` with the current totals to every destination that still expects goods. Koomyo (from its code, not a live run) says `close_short` at a destination where nothing arrived is allowed: each line's current total (0) plus `close_short` closes what is still expected there without booking a delivery, and `nothing_to_receive` is only answered without `close_short`; that is what the app sends. If it behaves differently the Event Log shows the answer. `destination_required` cannot occur because the app always names the destination.
- **Coming in.** A Koomyo-made order with allocations becomes one Purchase Order row per share, each for the Warehouse of its destination (a branch's, or the Koomyo warehouse's mapped Warehouse). Each delivery becomes a Purchase Receipt of the rows for the Warehouse it landed at (`location_type`, `location_id`), filled row by row when one ingredient has several shares there. A place with no Branch Map row is `NeedsMapping` naming its id.
- **Transfers.** Goods in a warehouse reach branches by transfers staff make; the existing `transfer.sent`/`transfer.received` steps post them (Transit Warehouse needed). The request line's `received_quantity` is Koomyo's; nothing is computed here.
- **Not verified live:** every part of this; the fake Koomyo plays the documented rules and error codes. The live restaurant does not have the feature.

## 20. Supplies, low stock, deleted open counts, payment methods (Decision / Open)

- Items 18 and 20 are confirmed as built by Koomyo (naming rules, the supplies expense mapping, skipping `stock.low`, ignoring deleted open counts). Payment Map: Set Up From Koomyo already reads `GET /payment-methods`; unknown codes can still appear, so the Default Mode of Payment fallback stays.
- **Supplies.** `kind` (`food`, `packaging`, `supply`) and `supply_category` are on ingredients, stock levels and their events. The Item keeps `koomyo_kind`. The movement `supply_issue` (manual, arrives as `stock.adjusted`, positive when an issue is undone) is booked to the connection's **Supplies Expense Account** (NeedsMapping when empty), never Cost of Goods Sold or Stock Adjustment. Supplies are not in `stock.usage_daily`, so daily usage never includes them. Food versus packaging is not told apart in ERPNext (both keep their kind on the Item).

- **Payment methods.** The code list is never assumed. A method not in the Payment Map fails with the row to add (CLAUDE.md: a missing mapping is never guessed), unless the connection has a Default Mode of Payment with a default account for the Company, as the brief asked: then it is booked there, the Payment Entry's remarks say so, and the Event Log row carries a warning. Fees are not applied to such a payment.

## 21. Cancelling a purchase order from ERPNext (Built)

`POST /purchase-orders/{id}/cancel` (scope `purchasing.write`, body `{"reason"}` 1 to 300 characters, optional Idempotency-Key) now exists. Cancelling a Purchase Order that was sent to Koomyo queues `erpnext.purchase_order_cancel`, which sends it with the reason "Cancelled in ERPNext (<PO name>)" and a note on the Purchase Order. What the order held goes back to the purchase requests (an ordered request line becomes approved again, and Koomyo sends the request events, so the Material Request is made again as needed). `purchase.cancelled` comes back and changes nothing (the order is already cancelled). Answers: 409 `already_cancelled` is the job done; 409 `partially_received` fails with how to finish it (close it short: receive what arrived and `close_short`); 409 `already_received` fails saying the stock has to be adjusted in Koomyo; a retry after a refusal uses a fresh Idempotency-Key (Koomyo replays refused answers for the same one). Nothing is sent for an order never sent to Koomyo or made by Koomyo, or on a Read Only connection. Editing an order through the API is still not available, so a change of a sent order in ERPNext (other than a cancel) does not reach Koomyo. Not run against a live Koomyo.

## 22. Tax and charges on an order made in ERPNext (Built, with limits)

`POST /purchase-orders` now takes, all optional: on the order `tax_name`, `tax_rate`, `tax_mode`, `tax_recoverable`; on a line `tax_percent`, `tax_exempt`, `discount_percent`, `pack_note`; and `charges[]` (`label`, `kind`, `value`, `direction`, `tax_percent`, `spread_over_cost`, `role`, `taken_of`). Koomyo calculates the totals itself with the admin's rules; only the inputs go and its `total_ordered` is read from the answer (never recomputed), noted as a comment on the Purchase Order, and a difference of 1.00 or more from ERPNext's own total is warned on the Event Log row.

How ERPNext's Purchase Taxes and Charges map (`sync/purchasing.py: tax_fields`):
- a row on the **Withholding Tax Account** is a charge with `role` withholding (a deduction, amount);
- a row on the **Purchase Tax Account**, or on an account of type Tax, is the order tax: its rate (an "On Net Total" row's rate, else the amount over the net total to 4 places), `tax_mode` inclusive when the row is included in the print rate, `tax_recoverable` true only for category Total (a "Valuation and Total" tax is not recoverable);
- any other row is a charge (amount, add or deduct); on the **Landed Cost Account** it is spread over cost as Charges in Landed Cost says (By Quantity, None, else by value), and a Valuation row elsewhere is spread by value;
- a line's `discount_percentage` goes as `discount_percent` on the price before the discount; with prices included in the tax, the gross rate is sent.

What cannot be said goes in the notes with a warning, never guessed: a second tax (Koomyo takes one order tax; per-line `tax_percent` is not derived from ERPNext's item tax templates), a discount on the whole order, a tax with no net total to work out its rate, more than 20 charges. Koomyo's rounding can differ from ERPNext's by a few cents. `pack_note` and `tax_exempt` are not sent. Combined with shares, as Koomyo allows. Not run against a live Koomyo: the fake plays the inputs and a simplified calculation.

## 23. ERP mode and the close at a destination (Built)

- **`GET /account` `purchase_requests`.** `enabled` (the Inventory app and the purchase requests feature are on) and `handled_by` (`koomyo` or `external`, null when not enabled). Test Connection stores it (a hidden field, "enabled:external"), and with Sync Purchase Requests on it warns when the feature is not enabled (and does not probe `GET /purchase-requests`), and warns when `handled_by` is `koomyo` (purchasing there still orders: whoever orders a line first wins; set it to the external system). It is quiet when an external system orders. A Koomyo whose answer has no `purchase_requests` is probed with `GET /purchase-requests?limit=1` as before. The 5-minute read of requests checks `GET /account` again if the last state was "disabled", and reads requests only once it is enabled. The README tells the user to set ERP mode and not to press Send on an order ERPNext made, as before.
- **Closing a destination short.** A Purchase Order closed in ERPNext is sent as `destination_type` + `destination_id` + `close_short` with every line at its current total at that place (0 where nothing arrived): no stock moves, no lines are booked, and Koomyo writes one closing receipt with no lines. A repeat answers 409 `nothing_to_receive`, which means the first close worked: the place is counted as already closed (Skipped, no third receipt). The order's other places are not touched. Tested against the fake Koomyo only.

## 24. Where a share goes, and orders that stay drafts (Decision / Open)

- **Share destinations follow the Purchase Order row.** With "Koomyo decides" a share of an order from a branch's request went to Koomyo's main warehouse, while the ERPNext row (and its Purchase Receipt) was at the branch's own Warehouse, so the receive failed with `400 invalid_parameter: No item on this order is delivered to that place`. Each share now names its destination from the row's Warehouse on the Branch Map: a branch's Warehouse is `branch` (and must be the request's own branch, else the order is refused before anything is sent), a Warehouse of Location Type Warehouse is `warehouse` with that warehouse's id. The receive then names the same place. The **Deliver Shares To** setting is no longer sent (kept so existing connections load). An order already sent with the old behaviour cannot be changed (no edit call): cancel it (a cancelled Purchase Order is cancelled in Koomyo) and make it again.
- **Drafts (answered by `mark-ordered`, built).** After creating an order, the app now calls `POST /purchase-orders/{id}/mark-ordered` (with the order's `updated_at` and the Purchase Order's required-by date as `expected_date`), so it is ordered in Koomyo and nothing is emailed; the setting **Mark Sent Orders as Ordered** (on by default) can switch it off. 409 `not_a_draft` is fine, 409 `stale_version` re-reads the order once, 409 `delivery_places_incomplete` fails the event after the order exists (a Retry marks it, never a second order). The app never calls `/send` (scope `purchasing.send`). Not run against a live Koomyo. Earlier text, kept for the record: `POST /purchase-orders` always creates a draft in Koomyo (docs: "an order you post is a draft that staff can still edit"); there is no field or call to mark it ordered, so an order submitted in ERPNext stays a draft in Koomyo until staff mark it ordered or send it there (Send emails the supplier, which ERPNext already did). Whether Koomyo accepts a receive on a draft was not documented and not tested against a live Koomyo. **Wish:** an `ordered` flag on create (or `POST /purchase-orders/{id}/order`), so an ERPNext order is a commitment in Koomyo without sending it.

## 26. Editing a sent order (Built)

`PATCH /purchase-orders/{id}` (scope `purchasing.write`) is sent when a submitted Purchase Order that this app sent is changed in ERPNext (Update Items: quantity, rate, new or removed rows; ERPNext fires no event for its Close button, but `on_update_after_submit` fires for these). The app reads the order, and sends the complete `lines` (every existing line id kept, matched by ingredient; a new row has no id; a row removed in ERPNext is left out and Koomyo drops it with its shares), each line with its shares again (a line you send replaces that line completely), the complete `charges` (`[]` removes them) and the tax (`tax_rate` 0 removes it), `notes`, `expected_date` and the `updated_at` it read. `409 stale_version` re-reads once and repeats. A **partly received** order gets only `notes` and `expected_date`; what ERPNext changed that Koomyo then freezes (a quantity, a price, a new line) is listed in a warning on the Event Log row, never forced. A received or cancelled order is locked (`po_locked`): the event fails and says Purchase Order was changed in ERPNext only. An order Koomyo made (or never sent) is not edited there. Koomyo's total from the answer is noted on the Purchase Order. ## 27. Cancelling a receipt (Built)

Only receipts the app sent carry the hidden `koomyo_sent` mark; a receipt made from a Koomyo delivery is left to Koomyo. ## 28. Invoice price differences (Built, opt in)

`POST /purchase-orders/{id}/receipts/{receipt_id}/restate-costs` (scope `purchasing.write`) corrects only the unit cost of the listed lines of one delivery. The docs say to call it only when your system corrects prices after the invoice, so it has its own switch on the connection, **Send Invoice Price Differences** (off by default). When it is on and a Purchase Invoice is submitted against a Purchase Receipt this app sent, every row whose invoiced unit cost (net rate in the ingredient's unit, as for the order) differs from the receipt row's is sent with `reason` ("Supplier invoice <bill no>"), the line ids of that delivery and the order's `updated_at` (`stale_version` re-reads once). A receipt spanning several places is restated delivery by delivery. `receipt_reversed` fails the row and says so. The answer's `cost_rule` is read: with mode `ask`, Koomyo made a suggestion for a person, and a warning on the Event Log row says so (`auto` and `off` need no word). Returns are not restated. Quantities are never sent.

Not verified: the real server (the fake plays the documented rules). Worth knowing in ERPNext: a Purchase Invoice with another rate than its Purchase Order or Receipt is refused unless **Maintain Same Rate Throughout the Purchase Cycle** is off in Buying Settings, and billing above the order needs **Over Billing Allowance** in Accounts Settings. That is ERPNext's rule, not the app's; the app does not change those settings. "Landed unit cost" (the field's wording) is taken as the net rate, not including the purchase taxes or landed cost vouchers: the docs do not say more.

## 29. Goods sent back to the supplier (Built)

A submitted ERPNext Purchase Return (a Purchase Receipt with `is_return`) against a receipt this app sent becomes `POST /purchase-orders/{id}/returns` (scope `purchasing.write`): `reason_code`, a `note` ("ERPNext return <name>"), the `lines` (order line id and the quantity, always positive, in the ingredient's unit) and the order's `updated_at` (`stale_version` re-reads once). The reason comes from a new field on the return, **Reason For Koomyo** (Damaged, Wrong item, Quality, Other; empty is `other`), because ERPNext has no such field. The place (`destination_type` and `destination_id`, from the return's Warehouse on the Branch Map) is sent only when the order was received at more than one place, as the docs say; a return that takes goods from several warehouses at once is refused with a message (Koomyo takes one place per return: make one return for each). Refusals say what to do: `return_exceeds_received` (a line cannot go back for more than arrived at that place, less what already went back and what moved on by transfer; ERPNext cannot know what staff returned in Koomyo's admin), `destination_required`. `below_zero` is a warning on a Done row. ## 30. Closing short (Built; replaces the close through `receive`)

Closing a Purchase Order in ERPNext now follows the docs' rule: **`POST /purchase-orders/{id}/close-short`** when nothing more is arriving (a close with nothing delivered), body `reason_code` `short`, a `note` ("Closed in ERPNext (<order>)") and the order's `updated_at` (`stale_version` re-reads once); **`close_short` on the receive call** only when the last delivery and the close are one act (a Purchase Receipt made while the order is Closed: it also sends `reason_code` `short` and a `reason_note`). Before, a close went through `receive` with every line's total so far. An order with branch shares is closed place by place (`destination_type` and `destination_id`), only the places that still expect goods, and each call carries the version the last call answered with. 409 `nothing_to_receive` (already complete or closed) is Skipped, so a retry is safe. Orders that are `ordered` or `partial` can be closed; an order with nothing delivered, which was skipped before, is now closed too. **Unsure, not tested live:** what Koomyo answers for an order still a `draft` (the docs list no code); the app shows Koomyo's own message. The reason code is always `short`: ERPNext has no reason on its Close button.

## 31. Stock transfers made in ERPNext (Built, opt in)

Scope `transfers.write`; switch **Send Stock Transfers to Koomyo** on the connection (under Sync Stock, off by default, so the scope is asked for only when it is on). Only warehouses on the Branch Map are Koomyo's business.

- **A plain Material Transfer** (stock moved at once in ERPNext): `POST /stock-transfers` (not a draft: sent at once, the stock leaves the source), then `POST .../receive` for every line, so Koomyo's stock matches ERPNext's. The entry's name is the transfer's `reference` and `external_ref`; the entry keeps the Koomyo transfer id and is marked sent. A retry after a failed receive finds the transfer and only receives (never a second transfer; a lost answer is also safe, because the same `external_ref` returns the same transfer with 200).
- **In steps** (Send to Warehouse into the Transit Warehouse, then Receive at Warehouse): ERPNext does not know the destination when it sends (it is chosen when the stock is received; checked in `make_stock_in_entry`), and Koomyo's `to` is required, so **nothing goes to Koomyo at the send**. The first Receive at Warehouse makes the transfer (what the send held, from the send's warehouse to the receive's warehouse) and receives what arrived; later ones are later deliveries (`receive` with this delivery's quantity). What did not arrive stays in transit on both sides until resolved. The send's warehouse must be the connection's Transit Warehouse.
- **Resolve:** a Receive at Warehouse that puts stock back where it was sent from is `resolve` kind `returned`. A **loss** is not sent: ERPNext has no document that names its transfer, so a loss is decided in Koomyo and booked here by the inbound sync as before.
- **Cancel:** cancelling the send (or the plain transfer) in ERPNext is `POST /stock-transfers/{id}/cancel` with a reason. Koomyo refuses once goods arrived (`transfer_partially_received`): the Event Log row says to resolve the rest there or make a transfer back. Cancelling a delivery or a resolution has no Koomyo call: the row is Skipped with that message. A transfer Koomyo cancels is not cancelled back.
- **Drafts:** an ERPNext draft moves nothing, so nothing is sent; Koomyo's draft transfers (`draft: true`, `POST .../send`, `PATCH`) are therefore **not used**. The send is a transfer made without `draft`.
- **No doubling:** Koomyo's own events for what ERPNext made (`transfer.sent`, `.received`, `stock_transfer.completed`) find the entries by `reference`/`external_refs` (the entry is stamped on the spot if our own call has not yet), and each delivery or resolution by its `note` ("ERPNext <entry>"), and book nothing. A transfer made in Koomyo is never sent back.
- Quantities are the entry's stock quantity in the ingredient's unit with three decimals; more decimals fail with a message (Koomyo's limit). One source and one destination per entry (Koomyo's limit).

Not verified: the real server (the fake plays the documented rules); `PATCH` and `send` untested because unused; the `reference` rule (unique over transfers) would refuse a Stock Entry whose name was already used as a reference in Koomyo (`reference_in_use`, a Fatal with a message).

## 32. Physical stock changes made in ERPNext (Built, opt in)

Scope `stock.write`; switch **Send Stock Changes to Koomyo** on the connection (under Sync Stock, off by default). **Nothing is sent unless the document is marked**, and never sales (Koomyo takes sales off stock itself): a new field **Send To Koomyo As** on a Material Issue or Receipt (Adjustment, Waste, Supply issue), and **Send To Koomyo As A Stock Count** on a Stock Reconciliation. A marked document whose warehouse is on no connection's Branch Map shows a message when it is submitted.

- **Adjustment** (breakage, a found box): one `POST /stock-adjustments` for each row, signed quantity (an issue is negative; four decimals at most), `reason` "ERPNext <entry>" (never one of the system codes, which Koomyo refuses with `invalid_reason`), the remarks as `note`, `external_ref` "<entry>#<row>". Cancelling sends the opposite adjustment (Koomyo has no delete).
- **Waste:** one `POST /waste`, a line for each row, each with its own `external_ref`; the reason (`staff_meal`, `comp`, `tasting`, `spoilage`, `other`) comes from the **Waste Map** by the rows' expense account, the reverse of how Koomyo's waste is booked; an account that is not on the map is `NeedsMapping`, rows of different reasons are refused. A supply answers 400 `supply_not_allowed`: the row says to send it as a Supply issue. Koomyo has no undo for waste: cancelling leaves a Skipped row saying so.
- **Supply issue:** one `POST /supply-issues` for each row (reason `used`; `damaged`, `lost` and `expired` are not chosen from ERPNext). 403 `feature_not_available` says the Supplies switch is off in Koomyo. Cancelling calls `POST /supply-issues/{id}/undo`; `already_undone` is fine.
- **Count:** for each warehouse on the Branch Map, `POST /stock-counts` (with an `external_ref`, so a retry finds the same count), `PUT .../lines` with the counted quantities of the Items linked to ingredients (other warehouses' rows are left out, with a warning), then `POST .../close`. `already_closed` and `count_closed` on a retry mean it is done. A closed count is locked, so cancelling the reconciliation leaves a Skipped row saying so. `DELETE /stock-counts/{id}` (an open count) is **not used**: a count left open after a failure is finished by Retry.
- **Echo:** each Koomyo record is stamped on the row (`koomyo_line_id`); Koomyo's own `stock.adjusted`, `waste.recorded` and `stock_count.closed` events for them are Skipped when the record's `external_refs` names the ERPNext document, or a row of ours already holds the record's id (or the `reference_id` behind the movement).

Not verified: the real server (the fake plays the documented rules). **Unsure:** whether the `stock.adjusted` movement of a supply issue carries our `external_refs` or only a `reference_id` (both are checked); the id of a count's `stock_count.closed` event is assumed to be the count's id.

## 33. Ingredients and warehouses made in ERPNext (Built, opt in)

Scope `ingredients.write`; switch **Send Items and Warehouses to Koomyo** on the connection (under Sync Stock, off by default). Nothing is created unless you mark it.

- **Create:** a stock Item marked **Send To Koomyo As** (Food, Packaging, Supply) is `POST /ingredients` with its name (150 characters), unit (the UOM Map read backwards; a UOM with no Koomyo unit is `NeedsMapping`), kind, the Item's valuation rate as the opening cost, `active` and `external_ref` = the Item code. **Opening stock is never sent** (the docs: a stock adjustment, never a field). The Item keeps the ingredient id. `name_in_use` and a supply with the Supplies switch off are said plainly. With more than one connection sending Items, the Item also says which (**Koomyo Connection To Send To**).
- **Patch:** a linked Item's name, stock UOM and disabled flag are compared with `GET /ingredients/{id}` and only what differs is `PATCH`ed, so what the menu load just wrote sends nothing back (the row is Skipped). `unit_in_use` says the unit cannot change once the ingredient has recipes, stock, movements or purchase lines. Cost keeps its own push (item 24's `push_item_cost`).

(An Event Log row may name a document deleted since: links are no longer checked when a row is saved.)
- **Warehouses:** a Warehouse marked **Send To Koomyo As A Warehouse** is `POST /warehouses` (name 100 characters, address from the address lines, `external_ref`) and added to the Branch Map as a Location Type Warehouse row; one already on the Branch Map as a warehouse has its name, address and disabled flag `PATCH`ed. `name_in_use`, `place_not_allowed` (a key limited to a branch), `main_warehouse` and `warehouse_has_stock` are said plainly.
- **Not sent:** kind changes of a linked Item, `made_in_house`, pack groups, supply categories (`GET /supply-categories` is not read), the units list (`GET /units` is not read: the UOM Map is the check), and `GET .../cost-history`.

Not verified: the real server (the fake plays the documented rules); the `level` field of `low_stock_levels` in the answer was not needed (the PUT is sent whenever reorder levels change, and Koomyo writes nothing when nothing changes); `deactivate: true` in the 409 is not read, the app switches it off whenever the code is `in_use`.

## 34. Cash on delivery collected short or with extra cash (Built, fields read; not seen live)

`Order.cod_short` and `Order.cod_extra` are in the OpenAPI file; Koomyo said they would announce when the data is live, so this was tested only against the fake. Null or absent is "nothing special"; a value that is neither an object nor null fails the order with a message.

- **cod_short:** the order's payment is what was **collected**, so the Payment Entry matches the cash that arrived and the invoice is left with the shortfall unpaid. The figures are checked (`collected + shortfall = expected`, and they must agree with the order's `amount_due` and `amount_paid`: a mismatch books nothing). The reason is noted on the invoice. With **COD Shortfall Account** (new, on the connection, an expense account) a Journal Entry `cod-short:<order id>` debits it and credits the customer against the invoice, which clears the unpaid shortfall (a write-off). Without the setting the sale is booked, the invoice stays partly unpaid and the Event Log row says to set the account. It is not a refund and does not touch refund limits.
- **cod_extra:** the payment is exactly the amount due, so the extra is in no payment, total or tax. A Journal Entry `cod-extra:<order id>` debits the cash account of the order's cash payment (the rider holds it, so rider settlement includes it) and credits **Rider Extra Cash Account** (new, an income account), apart from the sale. Without the setting it is noted on the invoice and the row warns.
- A replay changes nothing (the invoice exists, and each entry has its own id). Orders booked before this change are not revisited.

For Koomyo: the shortfall goes to a write-off expense account and the extra to an income account, both chosen on each connection. Nothing more is needed from your side.

## 35. Keeping Koomyo draft orders as drafts (Built, opt in)

Connection switch **Keep Koomyo Draft Orders as Drafts** (under Book Orders Made in Koomyo, off by default; it needs that switch). A Koomyo draft (`status: draft`, "a plan, not a commitment") is then kept as a **draft Purchase Order** (docstatus 0): it moves no stock and posts no accounts, carries the Koomyo id, and has a comment saying it is a plan. Off, or without Book Orders Made in Koomyo, drafts are Skipped as before.

- **Edited in Koomyo:** the same draft is rebuilt in place (same name) when the copy differs (the fingerprint of supplier, lines, shares, charges and tax). A second copy of the same version changes nothing.
- **Ordered in Koomyo:** the same document is rebuilt if needed and submitted, and the reference is written back to Koomyo as for any order. Deliveries then book as usual.
- **Cancelled in Koomyo (`purchase.cancelled`):** the draft is deleted here (it moved nothing and has no history to keep); the Event Log row says so.
- **Deleted in Koomyo:** the API publishes no delete call for orders and no event for it (not in the OpenAPI file: unconfirmed whether Koomyo ever deletes a draft). So the five-minute `updated_since` safety net also asks `GET /purchase-orders/{id}` for each draft it keeps (at most 50 a run); a 404 queues the Event Log row `koomyo.purchase_draft_gone`, which deletes the draft. Any other error is not treated as gone.
- **Guards:** a Koomyo draft cannot be submitted by hand in ERPNext (the order becomes real only when it is ordered in Koomyo and this app submits it). Nothing is ever sent to Koomyo for a draft. A draft made in ERPNext (no Koomyo content) is never touched.
- Note: ERPNext's Purchase Order has no `remarks` field, so the old `remarks` text on orders made from Koomyo is not stored; the order's Koomyo number is in the linked records and Event Log.

Not verified: the real server (the fake plays the documented rules); Koomyo's behaviour when a draft is deleted (assumed 404 on `GET /purchase-orders/{id}`).

## 36. Keeping unapproved purchase requests as drafts (Built, opt in)

Connection switch **Keep Unapproved Koomyo Requests as Drafts** (under Sync Purchase Requests, off by default). A request with nothing approved yet (`submitted`, `awaiting_branch_approval`, or approved with no approved line) is then kept as a **draft Material Request** (docstatus 0, type Purchase), with the quantities the branch **asked** for (`quantity`, lines not rejected or cancelled), each row carrying its Koomyo line id, and a comment saying nothing is approved. It moves nothing and no reference is written back to Koomyo for it. Off, drafts are Skipped as before.

- **Edited in Koomyo:** the same draft is rebuilt in place (same name) when the asked lines change.
- **Approved:** the same document is rebuilt with the **approved** quantities and submitted (as for any approved request), and the reference is written back. Once submitted it follows the existing rules (rebuilt only while nothing was ordered from it).
- **Rejected or cancelled:** the draft is deleted (the row says so). A submitted Material Request is cancelled as before.
- **Deleted in Koomyo:** no event exists for it, so the five-minute safety net asks `GET /purchase-requests/{id}` for each draft it keeps (50 a run); a 404 queues `koomyo.purchase_request_draft_gone`, which deletes the draft. Other errors are not treated as gone.
- **Guard:** a Koomyo draft cannot be submitted by hand (its quantities are not approved: it could be ordered by mistake); the app submits it when purchasing approves.

## 37. A transfer that fulfils a purchase request line (Built; needs the Send Stock Transfers switch)

Koomyo's 2026-11-03 change: a transfer line may carry `request_line_id` (the request line, our `koomyo_line_id` on the Material Request row). The OpenAPI file shows it (409 `request_line_not_orderable`, 409 `request_quantity_exceeded`, 400 `invalid_parameter`, 403 `feature_not_available`; a transfer linked to a request line cannot be edited: 409 `request_transfer`).

- **Button:** **Create > Transfer from warehouse** on a submitted, Koomyo-linked Material Request (type Purchase). It asks for the source warehouse and makes a **draft** Material Transfer Stock Entry (`koomyo_erpnext.api.make_transfer_from_request`), one row per request row, from that warehouse to the row's warehouse (the branch's), for what is still needed (not ordered, not already on a transfer), linked by `material_request` and `material_request_item` (ERPNext's own `make_stock_entry` cannot do this for a Purchase request). The user reviews, edits and submits it.
- **Push:** `transfers_out.body_lines` sends `request_line_id` for each row whose Material Request row belongs to this connection, one line per request line (rows of one request line are added up). The same applies to the transfer made at a Receive at Warehouse in steps. A transfer without such rows sends none.

No limit is kept here: it is only what Koomyo said now. If Koomyo cannot be read, a warning is shown and nothing is blocked. Koomyo's answer on the push is the final word.

## 40. A Purchase Order number reused after a delete: cleanup and identity (Built, except the amended-copy point)

From Koomyo's report (live pizzaflex: PUR-ORD-2026-00003 deleted and recreated under the same number while Koomyo still held the old, received order linked to it).

1. **Clean up Koomyo first, on cancel and on delete.** Cancelling a Purchase Order sent to Koomyo, and deleting one (a new `on_trash` hook; the Koomyo id travels in the event, since the document is gone), runs the same cleanup, decided by what Koomyo holds: draft or ordered -> `POST .../cancel` (reason); **received** -> every delivery is reversed newest first (`POST .../receipts/{id}/reverse`, reason required: the stock is taken back out) and then it is cancelled; **partly received** -> closed short (`POST .../close-short`), never cancelled; already cancelled -> nothing. Then `DELETE /refs/purchase_order/{id}` removes the link (scope `refs.write`, now asked for by this handler). A step Koomyo refuses (a delivery already moved on by transfer or returned, a cancel refused) stops the rest, keeps the link and is reported on the Event Log row with a Retry. Running it twice changes nothing.
2. **Changed orders go to the same order.** Update Items on a submitted Purchase Order already is `PATCH /purchase-orders/{id}` with the last read `updated_at` (item 26; `stale_version` re-reads once); nothing is deleted and recreated. **Not possible:** *Cancel and then Amend*. The cancel reaches Koomyo within seconds and Koomyo has no call to un-cancel, so the amended copy (a new document with a new name) is a new order. Cancelling first is also what reversing the receipts needs.
3. **The number alone is not the identity.** Koomyo's `created_at` is compared with the ERPNext document's `creation` (a minute of slack): a Koomyo order made *before* the document existed cannot be its order. On a push that answers with such an order nothing is linked, marked or changed, and the row says the number was reused and the old order must be cleared (cancel it and remove its link), then Retry. The same check protects inbound events and the safety net: an order found only by the linked number (not by its Koomyo id) and older than the local document is refused with a message, never touched. (Koomyo's own `created_at` is used instead of storing a timestamp with the link, because the link is only a name and an id; the stored side is Koomyo's.) Also fixed: the Koomyo id used to be written on the Purchase Order *before* the total check, so a refused push left the old id on the new document; it is now written after the identity check.
4. **Idempotency key:** it names the document version (`modified`) and now a hash of the body, so the same key never carries another body (422 `idempotency_key_reused`).
5. **Total check kept:** after each push (create and PATCH) ERPNext's total is compared with Koomyo's; a difference larger than rounding stops it. A check *before* the push is not possible (Koomyo's total is only known after it computes the order); the identity check above is what stops a reused number before the total is even compared.

For Koomyo: PUR-ORD-2026-00003 was never re-sent from here (the live site is not this one); with the identity check a re-send is refused until the old order PO-2026-0004 is cleared. Not verified against the real server; the fake plays the documented rules.

## 41. A Purchase Order received at several Warehouses (Built)

Koomyo splits a delivery across places only when the order's lines carry shares (`allocations`). Before, an order whose rows were all in one Warehouse had no shares, so a receipt into another Warehouse landed at the order's one place in Koomyo (seen on PUR-ORD-2026-00001: 50 at the main warehouse and 70 at the Tariq Road branch, all 120 at one place).

- **Create:** rows of a Purchase Order in **several Warehouses** (and no Material Request) are one Koomyo line per ingredient with a share per Warehouse (`destination_type`/`destination_id` from the Branch Map, a branch share also with its `branch_id`; no `request_line_id`, so it needs no purchase requests feature). The shares add up to `quantity_ordered`; the order carries no `branch_id` (it follows its shares). A Warehouse that is not on the Branch Map stops the order with the row to add. A single-Warehouse order is unchanged (no shares). The hook that queues the order now also finds the connection when the rows are in several Warehouses (it used to find none and silently send nothing).
- **Receive:** an order with shares is received once for each place, with that place's total so far (already built, items 24 and 30).
- **Receipt at a place the order is not for (no shares):** refused before anything is sent: "Purchase Receipt X receives at Warehouse W, which is not the place of Koomyo order Y, and the order has no shares ... Give the Purchase Order one row for each Warehouse (Update Items), then press Retry." A Warehouse not on the Branch Map is not checked.
- **Changed order:** Update Items that moves the rows into several Warehouses sends the new split with `PATCH` (the complete lines with their shares, `updated_at`); the shares always add up to the line.
- **Already received without shares** (PO-2026-0033's case): cancel the Purchase Receipt (the delivery is reversed in Koomyo, item 2), change the Purchase Order's rows (one per Warehouse; the PATCH sends the shares), then make the Purchase Receipts again: each is received at its own place. This is a series of steps for a person; the app does not split an order by itself because the split is only known from where the stock is received.

Notes: the OpenAPI text for a share says `branch_id` may be left out only when a request line is sent; Koomyo's own example for this case sends only the destination and the quantity, which is what a warehouse share does here (a branch share also sends `branch_id`). ## 42. ERPNext refuses what Koomyo would refuse: a receipt at the wrong place (Built)

Before, the problem showed only after the receipt was submitted: the push failed (item 41). Now `before_submit` on a **Purchase Receipt** asks Koomyo for the order it belongs to (`GET /purchase-orders/{id}`, nothing about it is kept here) and blocks the submit with the reason when Koomyo would refuse or misplace it:

- the order has **shares** and the receipt is at a Warehouse that is none of the places of its shares (Koomyo answers that no item is delivered there).
A Warehouse that is not on the Branch Map is not checked, and only Purchase Orders this app sent are checked (an order Koomyo made has its own receipts). If Koomyo cannot be read, a warning is shown and nothing is blocked; the push then does the same check and fails with the same words, so nothing wrong is ever sent. The same idea is already in place for transfers that fulfil a request line (item 37: a pre-check before submit, with Koomyo's answer on the push as the final word). The rule itself is Koomyo's: it is read from the order, not copied.

## 43. Every share needs a branch (correction of item 41; Koomyo's live answer)

The live server refused a split order: `400 invalid_parameter: Line 1: every allocation needs a branch_id (it can be left out only when request_line_id names a request line)` (Event Log `rui2qpj107`). So the OpenAPI text was right and the example in Koomyo's message (a main-warehouse share with only the destination and the quantity) was not. Koomyo then confirmed: `branch_id` is the branch the quantity is **for**; for a warehouse share it is the branch the stock is meant for after distribution and `destination_id` is the warehouse; for a branch share `destination_id` defaults to the same branch.

Built: a share of a split order (rows in several Warehouses, no request line) now always carries its `branch_id`. A **branch** share is for its own branch. A share at a **central warehouse** has no branch in ERPNext, so the connection has a new setting **Branch For Warehouse Shares (its Warehouse)** (pick the Warehouse of a branch from the Branch Map): every warehouse share is sent for that branch. Without it the order stops with "Set Branch For Warehouse Shares on connection ..., then press Retry"; a central warehouse picked there is refused with "not a branch". A single-warehouse order and a request-line share are unchanged. `deliver_to` is not used. The fake now refuses a share without `branch_id` like the real server.

Open for Koomyo: is "the branch the stock is meant for" really one fixed branch for a central warehouse share, or should a share to the main warehouse need no branch at all (a plain stock-in at the warehouse)? We send the configured branch until told otherwise.
